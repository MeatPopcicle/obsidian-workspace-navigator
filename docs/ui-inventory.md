# UI Inventory — workspace-navigator

Generated 2026-08-03 from commit 525fd4d.

## Summary

Workspace Navigator is a standalone workspace manager for Obsidian that tracks named "workspaces" (a saved set of open files, folder-expansion state, and sidebar layout) without depending on the core Workspaces plugin. Its UI surfaces are: a native settings tab (`src/settings.ts`), a sidebar `ItemView` tree panel (`src/workspace-sidebar-view.ts`), a fuzzy-suggest switcher modal plus several style/picker modals (`src/workspace-modal.ts`), a status-bar item (`src/main.ts`), a ribbon icon that opens the sidebar (`src/main.ts`), and a file-menu (right-click tab) context menu for sending notes between workspaces (`src/main.ts`). There is no in-note rendering surface (no code blocks or Markdown post-processors).

## Settings surface

- A settings tab exists at `src/settings.ts` (`WorkspaceNavigatorSettingTab`), built entirely with the native Obsidian `Setting` API; no custom DOM forms.
- Sectioning is done with native `<details>`/`<summary>` elements via a local `section()` helper (`src/settings.ts:86-91`), not Obsidian's own accordion pattern. Five sections: "Saving & layout" and "Workspaces" and "Appearance" and "Theming (Style Settings)" start open; "Import & backup" and "Maintenance" start collapsed. Dependent sub-settings (e.g. "Maintain layout across workspaces" under "Remember navigation layout") are shown/hidden by toggling `settingEl.style.display` and are visually indented with a left border via the `.wn-setting-indent` class (`src/settings.ts:92-98`, styled at `styles.css:1408-1412`).
- Settings, grouped as displayed:
  - Saving & layout: "Remember navigation layout per workspace" (toggle), "Maintain layout across workspaces" (toggle, dependent/indented), "Auto-save on workspace switch" (toggle), "Auto-save on layout change" (toggle).
  - Workspaces: "Manual sort order" (toggle, with a description string that rewrites itself based on state), "Default group for new workspaces" (dropdown populated from existing groups), "Confirm before deleting" (toggle).
  - Appearance: "Highlight active workspace" (toggle), "Transparent switcher modal" (toggle), "Keyboard-shortcut hints in switcher" (toggle), "Show status-bar indicator" (toggle), "Show group in status bar" (toggle, dependent/indented).
  - Theming (Style Settings): a single row whose contents change based on whether the community "Style Settings" plugin is installed (checked via `this.app.plugins.enabledPlugins.has('obsidian-style-settings')`, `src/main.ts:168`). If present: a button "Open Style Settings" plus two toggles ("Show shortcut button in sidebar", "Show shortcut button in switcher"). If absent: a description prompting the user to install the community plugin.
  - Import & backup (collapsed by default): "Import from Obsidian core Workspaces plugin" (button), "Import and overwrite" (button, `.setWarning()`, wrapped in a confirmation modal since it deletes all existing workspaces first), "Auto-backup on save" (toggle), "Backup folder" (text field for an absolute filesystem path, dependent/indented).
  - Maintenance (collapsed by default): "Reset all workspace styles" (button, `.setWarning()`, wrapped in a confirmation modal), "Debug mode" (toggle).
- Persistence: all settings plus workspace storage (`workspaceManager.getStorage()`) and navigation-layout state are merged into one object and written through `saveData()` (`src/main.ts:246-268`), i.e. everything lives in the plugin's own `data.json`. Writes are serialized through a `saveQueue` promise chain to avoid races. Separately, when "Auto-backup on save" is on, the same combined object is also mirrored to an external file via Node's `fs` module at an absolute path (`src/main.ts:270-294`) — desktop-only, no-ops on mobile (`Platform.isDesktopApp` check).
- Unusual behavior: the "Default group" dropdown silently resets to "(None)" and re-saves if the stored default group no longer exists (`src/settings.ts:175-180`). The two destructive actions ("Import and overwrite", "Reset all workspace styles") both route through the shared `createConfirmationDialog` helper described below rather than confirming inline.

## Panel / view surfaces

**Sidebar tree view** — `WorkspaceNavigatorView`, `src/workspace-sidebar-view.ts` (registered as `VIEW_TYPE_WORKSPACE_NAVIGATOR`). Opened via the ribbon icon ("layout-template", added in `src/main.ts:75-77`), the command "Open sidebar navigator", or by revealing an existing leaf. Layout: a header row with right-aligned icon buttons (add group, add workspace, expand/collapse-all toggle, optional Style Settings shortcut, settings), followed by a scrollable tree of collapsible group headers containing workspace rows, which themselves can expand to show a per-file list. Interaction patterns: click-to-expand accordion groups/workspaces (chevrons), inline rename (row becomes a text input in place), drag-and-drop reordering of groups, workspaces, and files (custom drag-ghost element that follows the cursor, `.workspace-drag-ghost`), hover-revealed action buttons (edit/delete) that are otherwise `opacity: 0`, and a right-click context menu (`Menu` from Obsidian) on group/workspace rows for the full action set. Rendering technology: vanilla DOM via `createDiv`/`createEl`, no framework.

**Switcher modal** — `WorkspaceSwitcherModal`, `src/workspace-modal.ts` (extends `FuzzySuggestModal<string>`). Opened via the command "Open workspace switcher", or by clicking the status-bar item. Layout: a fuzzy-search input over a flat/grouped list of workspace "cards" (rows visually grouped under group headers rendered by the shared `renderGroupHeader()` helper in `src/group-header.ts`), with per-row inline icon, name (with optional color/bold/italic styling), an active-workspace checkmark, and hover-revealed rename/delete buttons. It reaches into Obsidian's undocumented `chooser`/`updateSuggestions()` internals (wrapped behind a small typed `ChooserInternals` interface, `src/workspace-modal.ts:20-35`) to drive custom keyboard shortcuts (arrow keys, Ctrl+Enter rename, Ctrl+D duplicate, Shift+Delete delete, Shift/Alt+Enter save-and-switch) via a replaced `Scope`. Supports the same drag-and-drop reordering as the sidebar, plus an optional "transparent" mode (`.workspace-switcher-modal-transparent`) that strips background/border/shadow from the prompt so cards float over the editor. Uses `@popperjs/core` (the sole runtime dependency in `package.json`) for popover positioning. Rendering: vanilla DOM.

**Workspace picker modal** — `WorkspacePickerModal`, `src/workspace-modal.ts` (extends `FuzzySuggestModal<string>`). Opened from the commands "Send current note to another workspace" / "...and switch", and from the tab context-menu items described below. Simple flat fuzzy list of workspace names with an icon, group tag, and an "already has this file" indicator; disabled rows for invalid targets.

**Style modals** — `WorkspaceStyleModal` and `GroupStylePickerModal`, `src/workspace-modal.ts` (extend `Modal`). Opened from edit buttons on workspace/group rows. Layout: stacked "cards" (`.workspace-style-card`) each with a label header — "General" (name/group `Setting` rows), "Icon" (an 8-column scrollable grid of Lucide icon buttons via `setIcon`, plus a "no icon" option), "Name Style" (color swatches plus bold/italic toggles) — with a live preview strip at the top that updates via inline style mutation as fields change. Rendering: vanilla DOM, native `Setting` rows nested inside custom card divs.

**Confirmation modal** — `ConfirmationModal`, `src/confirm-modal.ts` (extends `Modal`), invoked through the `createConfirmationDialog(app, {title, text, cta, onAccept})` helper. Layout: title (`<h3>`), a paragraph of explanatory text, then a Cancel button and a CTA button (`mod-cta`) in a `.modal-button-container`. This is a generic yes/no confirmation, not a typed-name confirmation; it guards against double-submission with an `accepting` flag and always closes in a `finally` block even if `onAccept` throws. Used for: deleting a single workspace or group (gated behind the "Confirm before deleting" setting), "Import and overwrite" (unconditional), and "Reset all workspace styles" (unconditional).

**Status bar item** — `src/main.ts:995-1072`. Shows an icon (workspace's own icon, falling back to its group's icon, hidden entirely if neither is set) and text (workspace name, optionally prefixed with its group as "Group › Workspace"). Regular click opens the switcher modal; Shift-click saves the current workspace directly (no modal).

**Ribbon icon** — one entry, "layout-template" / "Open workspace navigator", opens the sidebar view (`src/main.ts:75-77`).

**Context menu** — registered on the `file-menu` event (right-click on a tab), adds "Send to workspace", "Send to workspace and switch", and, if the file is open elsewhere, an "Open in N other workspace(s)" submenu listing those workspaces by name (`src/main.ts:632-722`). Also injects a small numeric/icon badge (`.workspace-tab-indicator`) directly into each tab header's `.workspace-tab-header-inner` (a core Obsidian element) to flag files open in other workspaces (`src/main.ts:1078-1128`).

No React or other UI framework is used anywhere; every surface is vanilla DOM construction through Obsidian's `createEl`/`createDiv` helpers.

## Visual language

- CSS class prefix: `workspace-` (e.g. `.workspace-sidebar-item`, `.workspace-group-header`, `.workspace-style-card`, `.workspace-drag-handle`) plus a secondary `workspace-navigator-` prefix for status-bar classes (`.workspace-navigator-status`, `.workspace-navigator-icon`, `.workspace-navigator-text`) and a `wn-` prefix for settings-panel and Style-Settings-driven classes (`.wn-settings-section`, `.wn-setting-indent`, `.wn-hide-guides`). `styles.css` is 1413 lines with roughly 180 rule blocks.
- **Prefix collision risk**: the dominant `workspace-` prefix directly overlaps the namespace Obsidian's own core UI uses for its real layout primitives (`workspace-leaf`, `workspace-split`, `workspace-tabs`, `workspace-tab-header`, `workspace-tab-header-inner`, and so on). This plugin's classes (`workspace-group-header`, `workspace-sidebar-item`, `workspace-drag-handle`, `workspace-suggestion-item`, `workspace-icon`, `workspace-tab-indicator`, etc.) don't appear to literally duplicate a specific core class name found in this codebase, but sharing the bare prefix is fragile: a future Obsidian core class addition could collide, and the code already injects its own `.workspace-tab-indicator` element as a child of the real core `.workspace-tab-header-inner` (`src/main.ts:1120-1124`), i.e. it mixes plugin-owned DOM into a core-owned container. Any shared design-system pass should give this plugin's classes a distinct prefix (its own `workspace-navigator-` prefix, already used for the status bar, is the natural candidate to standardize on).
- Obsidian CSS variables used: `--background-modifier-hover`, `--background-modifier-border`, `--background-modifier-form-field`, `--background-primary`, `--background-secondary`, `--text-normal`, `--text-muted`, `--text-faint`, `--text-error`, `--text-success`, `--text-accent`, `--text-accent-hover`, `--text-on-accent`, `--interactive-accent`, `--interactive-accent-hsl`, `--accent-hsl`, `--font-ui-small`, `--font-ui-smaller`, `--font-monospace`, `--font-weight-semibold`.
- Hardcoded values not derived from a theme variable (the cohesion pass's raw material):
  - Colors: the full 10-swatch icon/name-color preset palette is hardcoded hex (`src/workspace-modal.ts:109-118`): `#ef4444`, `#f97316`, `#eab308`, `#22c55e`, `#14b8a6`, `#3b82f6`, `#8b5cf6`, `#ec4899`, `#6b7280`, `#ffffff`. Two more hardcoded hex colors live in `styles.css` hover states for action buttons: `#4ade80` (add-group hover) and `#c4b5fd` (add-workspace hover), `styles.css:762,767`. The drag-ghost shadow uses a raw `rgba(0, 0, 0, 0.3)` instead of a theme shadow variable (`styles.css:407`).
  - Sizing/spacing: pixel values are pervasive and not tied to a scale: icon/button sizes (`14px`, `16px`, `24px`, `20px`, `12px`, `10px`), paddings/margins (`2px 6px`, `6px 12px`, `4px 8px`, `0.75em 1em`, etc.), border-radii (`4px`, `6px`, `8px`), and inline-styled row padding in `src/workspace-modal.ts:1685-1826` (`5px 75px 5px 38px`, fixed `28px` min-height, `24px` icon width) that duplicates/diverges from the sidebar's CSS-driven density instead of sharing one sizing source.
  - Font sizes appear as raw px/em values in several places (`11px` action-button text, `0.8em`/`0.85em`/`0.9em` muted labels, `1.4em`/`1.5em`/`3em` icon previews) rather than the `--font-ui-*` scale used elsewhere in the same file.
- Design tokens on `:root`: none defined by this plugin. Instead it defines a set of Style-Settings-driven CSS custom properties consumed with fallback defaults throughout `styles.css` (`--wn-hover`, `--wn-active-bar`, `--wn-active-fill`, `--wn-checkmark`, `--wn-guide-color`, `--wn-count-color`, `--wn-dup-bg`, `--wn-density`, `--wn-font-scale`, `--wn-bar-width`, `--wn-check-size`, `--wn-radius`) — these function as a de facto small token set for the sidebar/switcher (color + spacing + sizing), but they are theming knobs rather than a general spacing/type/radius scale, and most of the plugin's own CSS still uses raw px alongside them.
- Icons: Lucide icons exclusively, via Obsidian's `setIcon()` (imported from `obsidian`), including a large curated list of ~120 icon names offered in the icon picker grid (`src/workspace-modal.ts:44-97`). No unicode glyphs or a custom icon system; one CSS comment calls out a "Legacy inline icon class" (`.workspace-icon`, `styles.css:478`) that still uses `font-family: var(--font-monospace)` as if for emoji/text icons, suggesting a prior icon system that hasn't been fully cleaned up.
- Style Settings integration: yes, a full `/* @settings */` block at the top of `styles.css` (lines 5-139) exposing a heading ("Workspace Navigator") with three sub-sections (active-workspace colors, guides/colors, sizing), covering the `--wn-*` variables above via `variable-themed-color`, `class-toggle`, and `variable-number-slider` entries. The settings tab also surfaces a direct link into the Style Settings tab when that community plugin is installed (`src/main.ts:171-177`).

## Feedback & confirmation idioms

- Success/error reporting is exclusively bare Obsidian `Notice` calls scattered through `src/main.ts`, `src/workspace-modal.ts`, and `src/workspace-sidebar-view.ts` (e.g. `new Notice('Saved workspace: ...')`, `new Notice('Failed to add file to workspace ...')`). There is no themed notice wrapper, no inline success/error boxes, and no distinct styling between success and failure notices; both are Obsidian's default toast.
- Destructive-action confirmation is a single reusable modal class, `ConfirmationModal` in `src/confirm-modal.ts`, invoked through `createConfirmationDialog()`. It is a plain title/text/CTA/Cancel dialog, not a typed-name confirmation and not a double-click confirmation. It is used for: single workspace/group deletion (only when "Confirm before deleting" is enabled in settings), "Import and overwrite" (always), and "Reset all workspace styles" (always). Some destructive UI paths skip it entirely by design: when "Confirm before deleting" is off, deletion (`src/workspace-sidebar-view.ts:1182-1194`, `src/workspace-modal.ts:1953-1983`) proceeds immediately with only a `Notice` afterward.
- No progress-bar or spinner UI exists anywhere; the one long-running-ish operation (writing a debug diagnostics report to disk, `src/main.ts:483-560`) completes synchronously from the user's perspective and just fires a `Notice` on completion.

## Shared-code relationships

- Nothing is imported from `obsidian-core-utilities`; a repo-wide search of `src/` found no reference to that package. This plugin's UI code is fully self-contained.
- Copy/paste candidates for a shared library: `ConfirmationModal`/`createConfirmationDialog` (`src/confirm-modal.ts`) is a small, generic, dependency-free confirmation dialog that is a natural candidate to hoist into `obsidian-core-utilities` for reuse by sibling plugins, as is the icon-picker grid pattern and the preset color-swatch row (both duplicated near-verbatim between `WorkspaceStyleModal` and `GroupStylePickerModal` inside `src/workspace-modal.ts`, e.g. lines 245-297 vs. 517-568) — the two modals differ mainly in whether they're editing a workspace or a group but repeat the same DOM-building code.

## Known warts

- The single `workspace-` CSS prefix is shared with, and risks future collision against, Obsidian's own core workspace-layout classes (see Visual language above); the plugin also injects its own element as a child of a core-owned `.workspace-tab-header-inner` container.
- A "Legacy inline icon class" (`.workspace-icon`, monospace-font-based) still ships in `styles.css` alongside the current Lucide-based icon system, suggesting incomplete cleanup after a past icon-system migration.
- Icon-color and name-style controls in `WorkspaceStyleModal`/`GroupStylePickerModal` are near-duplicated rather than shared, and their layout code relies on hardcoded inline pixel offsets (e.g. the workspace-row action-button positions `right: 32px` / `right: 11px`, matched by comment rather than by any shared constant) that would drift silently if the icon/button sizes ever changed.
- Several DOM areas mix CSS-class styling with directly-set inline styles for the "same" concern (group headers use inline JS for base styling per the comment at `styles.css:193-194`, "CSS classes here are for interactive states only"), which makes the visual language harder to retheme in one place and is a likely source of styles that quietly diverge from the CSS file.
- No accessibility-specific focus-state styling was found for interactive rows, drag handles, or action buttons beyond whatever Obsidian's own base styles provide; hover-only reveal of row action buttons (`opacity: 0` until `:hover`) has no equivalent `:focus-visible` reveal, which is a keyboard-accessibility gap.
- The 10-color preset swatch palette (`#ef4444`...`#ffffff`) and a couple of stray hex hovers in `styles.css` are the only fully hardcoded, non-theme-derived brand colors in the plugin; everything else legitimately needs to stay user-configurable per-workspace color, but the palette itself is a candidate for a shared constant if a cross-plugin color system is introduced.

## Constraints for the rulebook

- This plugin's central UI metaphor is a two-level tree (groups containing workspaces, workspaces optionally expanding to a per-file list) with drag-and-drop reordering at every level and inline rename; any shared visual contract needs to accommodate deep-nesting tree rows with connector "guide lines" (`--wn-guide-color`), not just flat lists.
- It relies on undocumented Obsidian `FuzzySuggestModal` internals (`chooser`, `updateSuggestions()`) to implement custom multi-key shortcuts inside the switcher modal; a shared UI contract should treat this as an existing, working pattern worth preserving rather than something to "clean up" during a cohesion pass, since replacing it risks breaking the switcher's keyboard workflow.
- Per-workspace and per-group user-customizable icon + color + bold/italic styling is a load-bearing feature (not decoration): any shared token/theming system must leave room for user-chosen, non-palette colors to override defaults, since the plugin's whole point is letting users visually distinguish many workspaces at a glance.
- The plugin already ships its own Style Settings integration (a `/* @settings */` block plus `--wn-*` custom properties for density, font scale, bar width, checkmark size, and row radius) as its de facto sizing/token system; a shared rulebook should either adopt this same variable-per-plugin-prefix pattern or provide a migration path, since users may already have saved Style Settings values keyed to the current `--wn-*` names.
- Desktop-only filesystem access (Node's `fs`, used for the optional local backup file) is gated behind `Platform.isDesktopApp` and must remain optional in any shared design, since this plugin explicitly supports mobile (`isDesktopOnly: false` in `manifest.json`) for its other surfaces.
